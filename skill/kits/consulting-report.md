# Kit · consulting-report

**System:** `executive` (see `../references/design.md`).
**Theme and layout:** `../references/themes.md` → Consulting Report.
**Audience:** decision makers and clients who must choose a direction and fund it.
**Reader task:** accept the diagnosis, compare the options, and commit to a
recommendation.

## Narrative

```
problem → conclusion (answer first) → issue tree → evidence → options matrix →
recommendation → roadmap and risks → appendix
```

The answer arrives early. The rest proves it is the right answer and shows how
to execute. A consulting deck is an argument with exhibits, not a tour of work
performed.

## Core page types

| Page | Job |
|---|---|
| Problem | Decision at stake, scope, constraints, criteria, owner, and timing. |
| Conclusion | The recommendation in one sentence, three reasons, condition, and ask. |
| Issue tree | MECE decomposition showing how the answer was reached. |
| Evidence | The exhibits that decide the case, each with a decision reading. |
| Options matrix | Options × explicit criteria, with recommendation and trade-off. |
| Recommendation | Choice, rationale, cost, risks, conditions, and kill criteria. |
| Roadmap / risks | Phases, owners, milestones, dependencies, gates, and stop conditions. |

Optional: market/context, financial model summary, implementation governance,
and appendix exhibits. Keep the body on the decision; move support to appendix.

## Content contracts and density

- One page carries one principal exhibit or reasoning object and one reading.
  A page with three equal charts has no point of view.
- Problem pages state at most three situation facts and explicit decision
  criteria. Do not recommend before the decision question is agreed.
- Answer pages give exactly three evidence-linked reasons unless the argument
  genuinely needs fewer; the condition and ask are not additional reasons.
- Issue trees use 3–4 MECE branches and 2–3 short leaves per branch. Mark the
  decisive branch and evidence status with labels, not color alone.
- Options matrices use 3–4 real options and 4–6 independent criteria. Weighted
  scores require agreed, defensible weights and a stated derivation.
- Recommendations include cost/resources, strongest counter-case, risk owner,
  trigger, and stop condition. Roadmaps use absolute dates and measurable gates.

## Evidence rules

- Every exhibit answers an issue-tree question; label it with that question or
  the conclusion it supports.
- Sources, periods, units, definitions, and comparison basis appear on the page.
  Market sizes and benchmarks are never invented; estimates show method/range.
- Options receive comparable evidence. Qualitative scores are labelled as such;
  never tune weights after seeing the result.
- Show the strongest reason against the recommendation and why it does or does
  not change the answer.
- Effort/duration estimates state their basis. A gate has a measurable criterion;
  a phase has one owner, not `the team`.

## Do

- State the answer on page two, then defend it.
- Make the issue tree visible and auditable rather than hiding logic in prose.
- Give the recommendation a cost, a risk, a condition, and an explicit ask.
- Put the `so what` next to the exhibit, not in a footnote.

## Don't

- Don't narrate the project timeline or the team's process as the argument.
- Don't use default consulting blue-and-gold unless the client's brand demands it.
- Don't use decorative SmartArt, card grids, or an emotion curve.
- Don't present unequal evidence as objective comparison or end on a roadmap
  without restating the decision.

## Anti-homogenization

- Page order is logic, not template. Some cases need two evidence pages and no
  issue tree; others need options before diagnosis.
- No two consecutive pages share a composition. Alternate exhibit-led,
  matrix-led, tree-led, and statement-led pages.
- Use at least four layout grammars in a ten-page deck and never run three
  matrices in a row. Adapt `themes.md`; do not copy a fixed exhibit geometry.
