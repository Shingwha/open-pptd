# Kit · consulting-report

**System:** `executive` (see `../../references/design.md` §2).
**Audience:** decision makers and clients who must choose a direction and fund
it.
**Reader task:** accept the diagnosis, compare the options, and commit to a
recommendation.

## Narrative

```
problem → conclusion (answer first) → issue tree → evidence → options matrix →
recommendation → roadmap and risks → appendix
```

The answer arrives early. The rest of the deck proves it is the right answer
and shows how to execute. A consulting deck is an argument with exhibits, not
a tour of the work performed.

## Required pages

| Page | Job |
|---|---|
| Problem | The decision at stake, scope, constraints, and what "good" means. |
| Conclusion | The recommendation in one sentence, with three reasons. |
| Issue tree | MECE decomposition showing how the answer was reached. |
| Evidence | The 2–3 exhibits that decide the case; each with a reading. |
| Options matrix | Options × criteria, with the recommendation marked. |
| Recommendation | The choice, the rationale, the risks, and the conditions. |
| Roadmap / risks | Phases, owners, milestones, dependencies, kill criteria. |

Optional: market/context page, financial model summary, implementation
governance, appendix exhibits. Keep the body to the decision; move support to
the appendix.

## Density and type

- Body 14–17 px; exhibit labels 10–13 px; source 9–11 px; titles 28–34 px.
- High density, but every page has one exhibit and one reading. A page with
  three equal charts has no point of view.
- Stable axes: exhibit title, chart/table, reading column, source line.

## Evidence rules

- Every exhibit answers a question in the issue tree; label the exhibit with
  that question or the conclusion it supports.
- Sources, periods, units, and definitions are on the page. Market sizes and
  benchmarks are never invented; if an estimate is yours, label the method.
- Options are compared on explicit criteria with weights or a rationale. A
  matrix without criteria is decoration.
- Show the counter-case: the strongest reason against the recommendation, and
  why it does not change the answer.

## Do

- State the answer on page two, then defend it.
- Make the issue tree MECE and visible; do not hide the logic in prose.
- Use one exhibit per page, with a title that states its finding.
- Give the recommendation a cost, a risk, and a condition.
- Put the "so what" next to the exhibit, not in a footnote.

## Don't

- Don't narrate the project timeline or the team's process.
- Don't use default consulting blue-and-gold unless the client's brand demands
  it; design from the content.
- Don't build card grids, decorative SmartArt, or an emotion curve.
- Don't present options with unequal evidence and call it objective.
- Don't end on a roadmap without restating the decision.

## Anti-homogenization

- The page order is a logic, not a template. Some cases need two evidence pages
  and no issue tree; some need the options before the diagnosis.
- No two consecutive pages share a composition. Alternate exhibit-led,
  matrix-led, and statement-led pages.
- Use at least four recipes in a deck of ten pages; never run three matrices in
  a row.
- `fragments/` are single-page geometry references. Never assemble them into a
  fixed deck and never copy the kit wholesale.
