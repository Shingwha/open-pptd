# Page recipe · issue tree

**Purpose:** show the logic of the answer. A good tree makes the analysis
auditable and the recommendation inevitable.

**Reader task:** see the question decomposed into MECE branches and know which
branch decides the case.

## Slots

1. Title: the question being decomposed.
2. Root: the decision question.
3. Branches: 3–4 MECE branches, each with a claim or sub-question.
4. Leaves: 2–3 evidence items or hypotheses per branch.
5. Mark: which branch is decisive and which is already answered (status, not
   color alone).
6. Source note: interviews, data, or assumptions behind the tree.

## Variants

**A. Horizontal tree** — root left, branches in a column, leaves to the right.
Best for a wide page.

**B. Vertical tree** — root top, three columns below, leaves under each. Best
for a projected page.

**C. Hypothesis tree** — branches phrased as testable hypotheses with a
verdict mark (confirmed / rejected / open). Use when the analysis is complete.

## Selection

A for a dense, text-heavy tree; B for a clean three-branch story; C when the
tree is the summary of the work. Do not use a tree with more than four
branches on one page — split it.

## Type and density

Root 16–20 px bold; branch 14–16 px; leaf 11–13 px. Keep the connector weight
uniform (1–1.5 px). Align every node to the same vertical rhythm. The tree is a
structure diagram, not a card grid: no filled boxes with shadows.

## Evidence / caption

The tree is a reasoning artifact, not data. Label assumptions and mark which
leaves are evidenced. If a leaf cites an exhibit, reference it.

## Do / Don't

Do: make branches MECE; mark the decisive branch; keep labels short.
Don't: use five levels; mix "how" and "why" branches; use decorative icons;
draw the tree with inconsistent arrowheads.
